# WSL2

## Objectif

WSL2 fournit l'environnement Linux principal du poste DevOps sans dual boot et sans partition EXT4 physique.

Architecture :

```text
Windows 11 Pro
└── D:\WSL\Ubuntu-DevOps\ext4.vhdx
    └── Ubuntu / ext4
        └── /home/<user>/projects
```

Les projets utilisés avec Docker, Terraform, Ansible, kubectl et Helm restent dans le système de fichiers Linux, pas sous `/mnt/c` ou `/mnt/d`.

## Profil principal V6 — standard

Le poste dispose de 48 Go de RAM et d'un Ryzen 7 7700 8 cœurs / 16 threads. Le profil quotidien limite volontairement WSL2 à 20 Go et 8 threads afin de conserver une marge confortable pour Windows, VS Code, navigateurs, Office et les applications desktop.

```ini
[wsl2]
memory=20GB
processors=8
swap=8GB
swapFile=D:\\WSL\\swap\\wsl-swap.vhdx
networkingMode=mirrored
dnsTunneling=true
firewall=true
autoProxy=true
nestedVirtualization=false
maxCrashDumpCount=3

[experimental]
autoMemoryReclaim=gradual
sparseVhd=true
bestEffortDnsParsing=true
hostAddressLoopback=true
```

Le profil est installé dans :

```text
%UserProfile%\.wslconfig
```

## Profils disponibles

### `standard`

```text
RAM WSL       20 Go
CPU WSL       8 threads
Swap          8 Go sur D:\WSL\swap\wsl-swap.vhdx
Réseau        mirrored
Usage         quotidien DevOps
```

### `lab-heavy`

```text
RAM WSL       28 Go
CPU WSL       12 threads
Swap          12 Go sur D:\WSL\swap\wsl-swap.vhdx
Réseau        mirrored
Usage         Kubernetes / builds / labs lourds
```

Ce profil laisse encore environ 20 Go de RAM physique et 4 threads logiques disponibles à Windows. Il ne doit pas devenir le profil quotidien par habitude.

### `nat-fallback`

Même budget que `standard`, mais réseau NAT. À utiliser uniquement si un VPN, un réseau d'entreprise ou un comportement particulier ne fonctionne pas correctement avec `mirrored`.

## Pourquoi ces limites ?

Sans configuration, WSL2 peut utiliser par défaut environ 50 % de la mémoire Windows, tous les processeurs logiques et un swap calculé à partir de la RAM. La V6 fixe explicitement les ressources pour rendre le comportement reproductible.

Le principe est :

```text
standard
Windows reste prioritaire
WSL reçoit assez pour Docker + Terraform + Kubernetes léger

lab-heavy
WSL reçoit davantage temporairement
Windows conserve néanmoins une réserve réelle
```

## Mémoire

`autoMemoryReclaim=gradual` permet à WSL de restituer progressivement la mémoire de cache au lieu de conserver inutilement une forte empreinte après un build ou un lab.

La V6 ne désactive pas le swap. Un dépassement ponctuel de mémoire doit ralentir proprement avant de provoquer un OOM brutal.

## Stockage

Le root filesystem Ubuntu reste dans :

```text
D:\WSL\Ubuntu-DevOps\ext4.vhdx
```

Le swap est déplacé vers :

```text
D:\WSL\swap\wsl-swap.vhdx
```

Les deux restent sur le second Crucial T705 et `D:` reste NTFS.

`sparseVhd=true` est conservé pour les nouveaux VHD afin d'éviter une allocation physique inutile de la taille maximale dès la création.

## CPU

`standard` utilise 8 threads sur les 16 threads logiques du Ryzen 7 7700.

`lab-heavy` utilise 12 threads.

La V6 ne donne jamais les 16 threads à WSL par défaut, afin d'éviter qu'un build, une compression ou un cluster ne rende l'interface Windows peu réactive.

## Réseau

Le mode quotidien est :

```ini
networkingMode=mirrored
dnsTunneling=true
firewall=true
autoProxy=true
```

Le réseau mirrored simplifie l'accès aux services locaux et s'intègre mieux avec le réseau Windows moderne. Le firewall WSL/Hyper-V reste actif.

`bestEffortDnsParsing=true` complète le DNS tunneling pour certains environnements DNS atypiques.

`hostAddressLoopback=true` autorise en mode mirrored l'utilisation des adresses IPv4 de l'hôte en plus de `127.0.0.1` lorsque cela est utile pour des labs réseau.

## Virtualisation imbriquée

```ini
nestedVirtualization=false
```

La stack cible utilise Docker Engine, kind et Minikube avec le driver Docker. Elle n'a pas besoin d'exécuter un hyperviseur imbriqué dans WSL2. Le réglage reste donc désactivé par défaut.

Si un futur lab exige réellement KVM dans WSL, ce besoin devra être traité comme un profil séparé et qualifié, pas activé globalement.

## `/etc/wsl.conf`

La distribution conserve :

```ini
[boot]
systemd=true

[automount]
enabled=true
mountFsTab=true

[interop]
enabled=true
appendWindowsPath=true

[network]
generateHosts=true
generateResolvConf=true
```

Pourquoi conserver l'interop :

- `code .` depuis Ubuntu ;
- lancement ponctuel d'un exécutable Windows depuis WSL ;
- intégration fluide VS Code / WSL.

## Changer de profil

Exemple lab lourd :

```powershell
.\scripts\bootstrap\06_wsl.ps1 -Profile lab-heavy
wsl --shutdown
wsl -d Ubuntu
```

Retour quotidien :

```powershell
.\scripts\bootstrap\06_wsl.ps1 -Profile standard
wsl --shutdown
wsl -d Ubuntu
```

Toujours utiliser :

```powershell
wsl --shutdown
```

après modification de `.wslconfig`.

## Qualification automatisée V6

```powershell
.\install.ps1 -Mode Verify -ValidateWsl
```

ou avec toute la stack Linux :

```powershell
.\install.ps1 -Mode Verify -ValidateWsl -ValidateDevOps
```

Le validateur contrôle notamment :

- hash exact de `.wslconfig` ;
- version WSL disponible ;
- Ubuntu réellement en WSL2 ;
- CPU réellement visible dans Linux ;
- mémoire réellement visible ;
- swap réellement visible ;
- `systemd` en PID 1 ;
- HOME sur EXT4 ;
- `~/projects` présent ;
- PowerShell 7 disponible côté Windows.

Verdict attendu :

```text
VERDICT: V6 WSL2 PLATFORM READY
```

Rapport :

```text
reports/wsl/validation-v6.json
```

## Avant une grosse session de jeu

Si WSL n'est pas nécessaire :

```powershell
wsl --shutdown
```

Cela libère complètement la VM WSL2 au lieu de conserver Docker/systemd actifs inutilement pendant la session gaming.
