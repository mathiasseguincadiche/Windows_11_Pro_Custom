# WSL2 — configuration actuelle

## Rôle dans la workstation

WSL2 fournit l'environnement Linux principal du poste DevOps sans dual boot et sans partition Linux physique.

```text
Windows 11 Pro
└── D:\WSL\Ubuntu-DevOps
    └── VHDX
        └── ext4 Ubuntu
            └── /home/<user>
```

Windows reste l'hôte ; Ubuntu sert de backend Linux pour Docker, Kubernetes, Terraform, Ansible, AWS CLI et les outils shell.

Pour apprendre WSL2 depuis zéro, voir [`16_WSL2_GUIDE_COMPLET.md`](16_WSL2_GUIDE_COMPLET.md).

---

## Contrat courant

```text
Distribution : Ubuntu
Version      : 26.04
Codename     : resolute
Stockage     : D:\WSL\Ubuntu-DevOps
HOME Linux   : ext4 dans le VHDX
systemd      : actif
```

Les projets Linux actifs restent dans :

```text
~/projects
~/labs
~/repositories
```

Les racines `/mnt/c` et `/mnt/d` ne sont pas les emplacements de travail principaux pour les outils Linux.

---

## Profil quotidien

Le poste dispose de 48 Go de RAM et d'un Ryzen 7 7700 8 cœurs / 16 threads.

Le profil quotidien est volontairement borné :

```text
RAM WSL       20 Go
CPU WSL       8 threads
Swap          8 Go
Réseau        mirrored
Usage         DevOps quotidien
```

Configuration représentative :

```ini
[wsl2]
memory=20GB
processors=8
swap=8GB
swapFile=D:\\WSL\\swap\\wsl-swap.vhdx
networkingMode=mirrored
dnsTunneling=true
firewall=true
autoProxy=true
nestedVirtualization=false
maxCrashDumpCount=3

[experimental]
autoMemoryReclaim=gradual
sparseVhd=true
bestEffortDnsParsing=true
hostAddressLoopback=true
```

Le but est de laisser une réserve confortable à Windows, VS Code, navigateurs, applications desktop et gaming.

---

## Profil lab-heavy

Pour Kubernetes, builds lourds ou labs temporaires :

```text
RAM WSL       28 Go
CPU WSL       12 threads
Swap          12 Go
Réseau        mirrored
```

Ce profil n'est pas destiné à devenir le défaut par habitude.

---

## Profil nat-fallback

Même budget que le profil quotidien, mais avec réseau NAT.

Il sert de solution de compatibilité lorsqu'un VPN ou un environnement réseau particulier ne fonctionne pas correctement avec `mirrored`.

---

## Pourquoi ces limites ?

Le principe est :

```text
quotidien
Windows reste prioritaire
WSL reçoit assez pour Docker + IaC + Kubernetes léger

lab-heavy
WSL reçoit plus temporairement
Windows garde une réserve réelle
```

Donner les 16 threads et presque toute la RAM à WSL n'améliorerait pas la workstation globale : cela rendrait simplement l'hôte moins prévisible.

---

## Mémoire

`autoMemoryReclaim=gradual` aide WSL à restituer progressivement de la mémoire après un build ou un lab.

Le swap reste actif. Un pic de mémoire doit dégrader les performances proprement avant de provoquer un OOM brutal.

Le projet ne désactive pas la compression mémoire Windows pour « optimiser » WSL.

---

## CPU

Le profil quotidien expose 8 threads Linux sur les 16 threads logiques du Ryzen 7 7700.

Le profil lourd en expose 12.

Cette répartition vise l'équilibre entre :

- Docker / Kubernetes ;
- Terraform / Ansible ;
- VS Code ;
- navigateur ;
- applications Windows ;
- réactivité de l'interface.

---

## Stockage

Le filesystem Ubuntu reste dans le VHDX situé sur le second Crucial T705.

Le swap WSL est également placé sur `D:` :

```text
D:\WSL\swap\wsl-swap.vhdx
```

`D:` reste NTFS ; le filesystem Linux existe **à l'intérieur du VHDX**, pas dans une partition physique EXT4.

`sparseVhd=true` est conservé pour limiter l'allocation physique inutile.

---

## Pourquoi les projets Linux restent dans `/home`

Docker, Git, Node, Terraform, Ansible et les outils Linux manipulent beaucoup de petits fichiers et utilisent des permissions/sémantiques POSIX.

Le chemin recommandé est :

```text
/home/<user>/projects
```

Plutôt que :

```text
/mnt/c/...
/mnt/d/...
```

Les montages Windows restent utiles pour échanger des fichiers, mais pas comme racine de travail quotidienne.

---

## Réseau

Le mode principal est :

```ini
networkingMode=mirrored
dnsTunneling=true
firewall=true
autoProxy=true
```

Le réseau mirrored simplifie l'accès aux services locaux et l'intégration avec Windows.

Le firewall WSL/Hyper-V reste actif.

`bestEffortDnsParsing=true` aide dans certains environnements DNS atypiques.

`hostAddressLoopback=true` permet l'accès à des adresses de l'hôte lorsque c'est utile pour les labs réseau.

---

## Virtualisation imbriquée

```ini
nestedVirtualization=false
```

La stack cible utilise Docker Engine, kind et Minikube avec le driver Docker. Elle n'a pas besoin d'un hyperviseur imbriqué dans WSL2.

Si un futur lab exige KVM, ce besoin devra être traité séparément et qualifié avant activation.

---

## `/etc/wsl.conf`

La distribution conserve :

```ini
[boot]
systemd=true

[automount]
enabled=true
mountFsTab=true

[interop]
enabled=true
appendWindowsPath=true

[network]
generateHosts=true
generateResolvConf=true
```

L'interop permet notamment :

- `code .` depuis Ubuntu ;
- l'appel ponctuel d'un exécutable Windows ;
- l'intégration VS Code / WSL.

## Changer de profil

Profil lourd :

```powershell
.\scripts\bootstrap\06_wsl.ps1 -Profile lab-heavy
wsl --shutdown
wsl -d Ubuntu
```

Retour au quotidien :

```powershell
.\scripts\bootstrap\06_wsl.ps1 -Profile standard
wsl --shutdown
wsl -d Ubuntu
```

Toujours redémarrer complètement la VM WSL après modification de `.wslconfig` :

```powershell
wsl --shutdown
```

## Validation

```powershell
.\install.ps1 -Mode Verify -ValidateWsl
```

Avec toute la stack DevOps :

```powershell
.\install.ps1 -Mode Verify -ValidateWsl -ValidateDevOps
```

La validation contrôle notamment :

- version/runtime WSL ;
- Ubuntu réellement en WSL2 ;
- ressources visibles dans Linux ;
- swap ;
- systemd ;
- filesystem du HOME ;
- racines de travail ;
- cohérence de la configuration WSL ;
- intégration PowerShell/Windows lorsque nécessaire.

Voir [`11_VALIDATION.md`](11_VALIDATION.md).

## Gaming

Si WSL n'est pas nécessaire pendant une session de jeu :

```powershell
wsl --shutdown
```

Cela libère les ressources de la VM sans modifier le profil permanent.
